**Issue:** The same pipeline was rebuilt by hand three times in one session: analyse a reference reel's style from frames (watch skill + ffmpeg contact sheets), write a ~150-word script, generate TTS, get per-word timestamps (upload or pin the generation as a flow asset node, then transcribe), hand-split caption groups that must match the transcript word-for-word, build scenes in Remotion, render stills on a contact sheet for review, render, deliver. Shared UI pieces only got extracted into a reusable module on the third video. Two non-obvious steps cost time: (1) the transcript word count must match the caption-group script exactly (a node check caught it); (2) when an asset-upload tool is unavailable, the speech generation itself can be pinned as an audio node and transcribed directly. Publishing to YouTube/TikTok via a connector then stalled because the rendered file had no permitted path to the connector's staged storage (temp-file hosts are blocked by the permission classifier) and the shared YouTube API quota was exhausted.

**Suggested improvement:** Create an `explainer-reel` skill: reference-style capture checklist (caption treatment, label pills, counters, progress bar, CTA ending), a reusable Remotion UI module (captions with keyword box, pill, counter, bar, clock, phone CTA) parametrised by palette, the voice → timestamps recipe (including the pin-generation-as-node fallback), the word-count assertion, the contact-sheet review step, and a publishing section that states up front that connector uploads need the file in the connector's storage and that the user's own app upload is the reliable default from a phone.

**Principle:** When a multi-step production workflow repeats within a single session, extract its reusable components at the second repetition, not the third, and record the environment's publishing constraints before promising automated delivery.

**Second instance (2026-10-23):** the user set a hard 45 s maximum (it is in their Instagram account name) after the three reels came out at 69.5 s, 53 s and 48.5 s. The Remotion project was gone with the old session, so they had to be shortened from the delivered .mp4 files: transcribe with word timestamps (faster-whisper; feed it ffmpeg-decoded f32 audio, because its PyAV call failed), drop whole sentences, and cut where three signals agree: a silence (silencedetect), the darkest frame of the scene fade (signalstats YAVG), and the frame where the burned-in caption switches. Cutting at the silence midpoint alone left 1–3 frames of the removed sentence's caption visible. The skill should carry the duration cap as a script-time limit (about 110–120 words at this voice), check the rendered duration before delivery, and keep this trim recipe as a fallback for when the source project is lost.

**Third confirmation (2026-10-23, Instagram):** the user asked to publish the three reels to Instagram. The Composio Instagram toolkit needs either a public `video_url` or a `video_file` s3key already in Composio storage, and a Business/Creator account connection. Neither path is reachable from the cloud container, so the app upload from the phone was again the working route. The skill should say this before offering to publish.

**Working publish route (2026-10-23):** nothing could move from the cloud container to the publisher. What worked: the user's own Drive held the source files. A connector workbench downloaded them, re-applied the recorded cut list with ffmpeg (run one at a time: three parallel 1080p encodes were OOM-killed) and checked each duration. It then staged each file to get a storage key, and created and published the reel from that key. The container needed about 1 to 2 minutes of processing, longer than the 60 s tool-call timeout, so polling had to run in short loops. The caption went out without hashtags because the tool's handling of `#` was unclear. Two more lessons for the skill. Keep the cut list (segment times) as the reproducible artefact, not the rendered file. And keep account identifiers out of notes pushed to a public repository: the classifier refused one such push.

**Fourth instance (2026-10-23, reel about sleeping under a blanket):** the user sent a new reference reel and asked for the same style on a new topic. The Remotion project and the shared UI module from earlier sessions were gone (videos/ is gitignored because the repository is public), so the whole UI was rebuilt from scratch again. Three new environment facts the skill should carry: (1) the render browser does not trust the container's proxy CA, so `@remotion/google-fonts` fails with `ERR_CERT_AUTHORITY_INVALID`; download the woff2 files with curl (which does trust it) into `public/fonts` and load them with `FontFace` behind `delayRender`; (2) point Remotion at the preinstalled headless shell (`/opt/pw-browsers/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell`) instead of letting it download one; (3) the voice used in earlier reels was never recorded, so the series voice cannot be kept consistent across sessions; the skill should name where the chosen voice id lives. The reference pace (267 words in 100.9 s, about 2.65 words/s) again matched the 110–120 word budget: a 115-word script came out at 42.3 s.
Two render traps from the same session: a module-level `delayRender` for font loading cleared fine in `remotion still` but timed out in every `remotion render` (even with a 4 s fallback timer), so fonts are now declared as base64 `@font-face` CSS with no `delayRender`, and they still render from frame 0; and a 12000 px CSS-3D grid floor plus a `blur()` spotlight cost about 3.6 s per frame under software GL, while the same floor drawn as perspective-projected SVG lines and a filter-free cone rendered 40 frames in about 30 s. The skill's UI module should ship the cheap versions.

**Fifth instance (2026-10-23, YouTube Shorts):** the same Drive → workbench → staged s3key route worked for Instagram (container created from the staged key). The YouTube upload with that same key failed with HTTP 429 `defaultVideoInsertPerDayPerProject` on the connector's shared Google Cloud project, the same quota wall seen in the first session. The quota belongs to the connector's OAuth app, not the user's channel, so a retry depends on other users' traffic after the daily reset (midnight Pacific). The skill's publishing section should check that quota first or say up front that YouTube uploads through this connector are best-effort, and offer the phone app upload as the default for YouTube. Renaming the channel through the connector was also refused by the permission classifier, so channel settings are the user's job in the app.

**Sixth instance (2026-10-23, smartwatch reel):** the user asked for a second reel in the same session with a "totally new" look, so the module must separate pipeline (fonts, captions alignment, scene clock, wipes, render config) from style (palette, shapes, caption treatment): the second reel reused align.py, the font embedding and the render setup unchanged and rewrote only the visual layer (light neo-brutalist stickers instead of the dark hologram). Voice credits: the speech tool's default of two takes doubled the cost and the second take failed with 427 of 10,000 credits left; one take was usable both times, so the skill should check the remaining balance first and default to one take when credits are low. The pace held again: 114 words came out at 40.6 s.

**Seventh instance (2026-10-24, "background sound" complaint):** after delivery the user heard a background sound under the voice. Diagnosis showed no added layer (render audio = source voice x0.705 plus codec delay) and silent mid-pauses (-70 to -87 dB); the voice itself carried a room-like tail and a low-mid murmur (150-500 Hz) after each phrase, worst in the first reel. Stationary denoisers (ffmpeg afftdn, noisereduce) did nothing; DeepFilterNet3 helped modestly, plus a 70 Hz high-pass and a gate on inter-phrase gaps built from the word timestamps. Lessons for the skill: (1) run a voice QA step before building scenes (tail decay after phrase ends, mid-pause level, spectrogram glance) and pick the cleaner take; (2) the DeepFilterNet GitHub model URL is blocked by the proxy, the fal/DeepFilterNet3 Hugging Face mirror works after converting model.safetensors to checkpoints/model_120.ckpt.best; (3) install heavy ML tools in an isolated uv venv (Python 3.11, torch 2.1.2 CPU): a global pip install of deepfilternet downgraded numpy and broke another installed tool until numpy was restored.

**Eighth instance (2026-10-24, "make it exactly like this reel"):** the user sent a 2:37 psychology reel and asked for an exact copy. Two constraints changed the brief before any work: the 45 s cap, and that a verbatim copy of another creator's script and design is not something to republish; the working answer was the same topic, structure and visual language with an original script, which the skill's reference-capture step should state up front. New facts for the skill: (1) the ElevenLabs balance ran out mid-pipeline (427 credits left, 669 needed for a 116-word script; `estimate_only` reports the cost but not the balance, only the failed run does), so the skill needs a credit check plus a no-cost fallback; (2) the fallback that worked was Kokoro-82M (`em_alex`, Apache-2.0) in an isolated uv venv: it needs torch 2.6 or newer (transformers refused 2.5.1), `lang_code='e'`, and no system espeak; it speaks about 3.1 words/s, so the same 116 words came out at 37.5 s, and generating sentence by sentence with computed gaps hit a 43.6 s target exactly; (3) Remotion's entry file must be `.tsx` when it contains JSX (a `.ts` entry fails in esbuild); (4) one bundle plus `renderStill` in a loop rendered 18 review stills in 7 s, far cheaper than one CLI `still` call each; (5) the render's audio sat at -29 dB mean, so a loudnorm pass (-15 LUFS) belongs before delivery.

**Ninth instance (2026-10-24, same session, 1:30 version):** the user then asked for the same reel at 1:30 instead of 2:30, a one-off override of the 45 s cap. Rebuilding at twice the length took one change that the skill should make the default: key every scene's start and end, and every in-scene beat, to word indices of the transcript (`W(i)`), never to hard-coded seconds. The second voice track then needed no retiming, and captions auto-group by punctuation with a five-word cap plus a short "never split before" list for names ("Timothy | Wilson"). Kokoro needed speed 1.02 and 0.2 s gaps to fit 243 words into 88.6 s; that pace is tight, so the skill's word budget for this voice is about 2.75 words/s, against 2.65 for the ElevenLabs voices.

**Tenth instance (2026-10-24, voice swap after a credit top-up):** swapping the provisional voice for an ElevenLabs one took minutes because scenes were keyed to word indices: a difflib alignment of the new transcript onto the fixed word list kept every scene index valid (0 unmatched of 236). Two more facts for the skill: (1) the run status returns a signed `content_url` per take, which curl downloads directly, so no asset-node detour is needed to get the file; (2) the v4 voice was 16 % slower than the budget (103 s for 243 words), and cutting every pause over 0.3 s to 0.3 s (counting pauses kept at 0.5 s), plus a 1.04 tempo, hit the 88.6 s target without audible speed-up. The take with the lower worst-pause floor (-64.5 dB median -87) was chosen as the voice QA step suggests.
